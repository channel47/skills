# Content Types

Six content types. Each has a natural home, a beat pattern, and channel adaptations. Match the nugget to the type, then the type to the channel.

---

## Build Log

**What it is:** What got built, what broke, what was learned. The primary content type. Screenshots, code, process. The reader walks away knowing how to do something or avoid something.

**Why it works:** Anyone can have a take. Few show receipts. Build logs are the differentiator.

**Natural home:** Newsletter (deep), X thread (compressed), LinkedIn (contextual)

**Beat pattern:**
1. Setup (the situation, 1–2 sentences). What was tried, why.
2. Tension (the failure, the longest section, 40–50%). What broke. Specific, technical, honest. This is the meat.
3. Turn (the shift). What changed. The insight, the workaround, the decision to start over.
4. Resolution (what worked, concise). Don't oversell. Credibility lives in understatement.
5. Kicker (one thought). Why this matters beyond the specific project.

**Channel adaptations:**
- *Newsletter:* Full beat pattern. Tension section can be 60% of the piece. Multiple sub-failures welcome.
- *X thread:* Compress to 5–8 tweets. Setup (1 tweet), tension (2–4 tweets), turn (1 tweet), kicker (1 tweet). Each tweet stands alone.
- *LinkedIn:* 2–3 paragraphs. Setup + the single most interesting failure + what it taught. Skip the full resolution.
- *X post:* Only if there's one killer line. "Spent the weekend getting an agent to handle deploys. It deleted staging twice. Then it worked. Then it didn't. Notes inside."

## Tool Report

**What it is:** Tested, not reviewed. Real usage on a real project with real stakes. Honest, specific, sometimes unflattering.

**Why it works:** The audience trusts tested verdicts because they come from use, not press releases.

**Natural home:** X post (short verdict), Newsletter (full report), GitHub (if code-adjacent)

**Beat pattern:**
1. Verdict (up front, no buildup). Like or dislike, stated plainly.
2. Context (what it was tested on). Real project, real constraints. This is what separates a report from a review.
3. Evidence (the detail). What worked, what didn't. Specifics.
4. Comparison (optional). What it replaced, or what it competes with.

**Channel adaptations:**
- *X post:* Verdict + one specific detail. "Used [tool] for two weeks on a real project. [One-sentence verdict]. [One specific observation]."
- *Newsletter:* Full beat pattern. The context section matters most here. Readers need to know the conditions to trust the verdict.
- *LinkedIn:* Verdict + context + the single most surprising finding.
- *GitHub:* Only if there's code involved. Document the integration, link to the fuller report.

## Contrarian Take

**What it is:** Something the space isn't saying, or is saying wrong. Not contrarian for sport. Contrarian because lived experience revealed something others are missing.

**Why it works:** Provocation forces reactions. But only when backed by experience.

**Natural home:** X post (sharp, single), LinkedIn (with more context)

**Beat pattern:**
1. The take (stated cold, no hedging). Lead with conviction.
2. The evidence (why this isn't just an opinion). What was seen, built, or experienced.
3. The concession (mandatory). What the other side gets right. A contrarian take without a concession is arrogance.
4. The reframe (why it still matters). Despite the concession, here's why the core observation holds.

**Channel adaptations:**
- *X post:* Just the take + one line of evidence. Let the replies provide the debate.
- *LinkedIn:* Full beat pattern in 2–3 paragraphs. The concession is what makes it work on LinkedIn (platform rewards nuance over heat).
- *Newsletter:* Only if the take has enough depth to sustain 500+ words. Most contrarian takes are X/LinkedIn material, not newsletter material.

## Process Note

**What it is:** How a decision got made. The thinking behind the building. Why this approach, not that one. Why this failed and that worked.

**Why it works:** Readers want the reasoning, not just the result. Process notes feel like getting access to someone's internal monologue.

**Natural home:** Newsletter (primary), LinkedIn (adapted)

**Beat pattern:**
1. The change (what shifted, stated plainly).
2. The old way (what was happening before, and why it seemed fine).
3. The signal (what made it clear it wasn't fine). This is the interesting beat. Not the change itself, but the moment of noticing.
4. The new way (what's happening now, with the honest caveat that it might not stick).

**Channel adaptations:**
- *Newsletter:* Full beat pattern. The signal section is the piece. Everything else is scaffolding.
- *LinkedIn:* Compressed. The signal + the change. 1–2 paragraphs.
- *X thread:* Only for major process shifts. Setup (old way, 1–2 tweets), signal (1 tweet), new way (1–2 tweets), kicker.
- *X post:* Only if the signal moment is killer. "Changed my whole publishing workflow this month. Not because the old one was broken. Because I noticed I was avoiding it."

## Shipping Update

**What it is:** Something released, updated, or made public. A new skill, a new repo, a new version, a public launch.

**Why it works:** Shipping is proof of work. But the update itself isn't the content. The story around it is.

**Natural home:** GitHub (primary), X post (announcement), LinkedIn (story)

**Beat pattern:**
1. What shipped (stated plainly, one sentence).
2. What it does (for the reader, not for you).
3. How to use it (one action, ideally one line).
4. What's next (optional, brief).

**Channel adaptations:**
- *GitHub:* README update. Clear, minimal, functional. Install command, what it does, how to use it.
- *X post:* "Shipped [thing]. [One sentence on what it does]. [Link]." Keep it tight. Don't oversell.
- *LinkedIn:* The story behind the ship. Why it was built, what problem it solves, one interesting detail from the build. 1–2 paragraphs.
- *Newsletter:* Only if the ship is significant enough to sustain depth. Otherwise mention it briefly and move on.

## Receipts

**What it is:** Numbers, screenshots, before/after comparisons, proof of work. The evidence that backs up everything else.

**Why it works:** Specific numbers anchor credibility. Screenshots prove the work is real. Before/after creates instant tension.

**Natural home:** X post (visual), LinkedIn (proof-point narrative)

**Beat pattern:**
1. The number or image (lead with it, no buildup).
2. The context (what produced this result, briefly).
3. The implication (what this means, one sentence).

**Channel adaptations:**
- *X post:* Number + one line of context. "25+ accounts running this workflow. Started with 1 three months ago." Attach screenshot if possible.
- *LinkedIn:* Number + context + what it means for the reader. "Here's what I learned scaling from 1 to 25."
- *Newsletter:* Receipts support other content types. They're rarely a standalone newsletter topic.
- *GitHub:* Stats in README. Stars, installs, accounts using it. Let the numbers speak.

## Matching Guide

When a nugget could be multiple types, pick the one that matches its strongest element:

| Strongest element | Type |
|-------------------|------|
| A specific failure and what was learned | Build Log |
| A verdict on something tested | Tool Report |
| An opinion that challenges consensus | Contrarian Take |
| A decision and the reasoning behind it | Process Note |
| Something that just went live | Shipping Update |
| A specific number or visual proof | Receipts |

If two types are equally strong, draft the primary type and note the secondary angle. A build log with strong numbers can also be a Receipts post. A process note that challenges how others do things can also be a Contrarian Take. Draft the dominant type, adapt the secondary.
